# ADR-0009: Threaded Tasks — Stable Task Identity Across Edits

**Status:** Proposed (design-only; promote to Accepted at Phase C kickoff post-soak) · **Date:** 2026-05-16 · **Soak-gated by:** [ADR-0007](0007-master-plan-v2.md) Phase A

**Full design spec:** [`docs/superpowers/specs/2026-05-12-P2-threaded-tasks-spec.md`](../superpowers/specs/2026-05-12-P2-threaded-tasks-spec.md)

---

## Context

Today the MTL (`10_Active Projects/Active Personal/!!! MASTER TASK LIST.md`) is a flat text file. Tasks identity = line text. Any edit, split, merge, re-extraction, or manual rephrase severs identity — Dataview queries lose history, completion rates drift, audit trails break. P2 in Master Plan v2 ([ADR-0007](0007-master-plan-v2.md)) is the move from line-as-identity to **stable `task_id` + backing file** so a task survives all of: edits, splits, merges, re-extractions, phone manual edits via Remotely-Save, cross-domain reclassification, completion sync.

## Decision

Adopt the design in `docs/superpowers/specs/2026-05-12-P2-threaded-tasks-spec.md`:

1. **Stable task IDs.** Every MTL line gets `[id:: t-2026wNN-XXXX]` (week-anchored slug + 4-char hash). Generated by `tools/task_id.py`; collisions detected; never reused.
2. **Backing files.** Each task gets `30_Tasks/<area>/t-2026wNN-XXXX.md` with YAML front-matter (canonical schema per spec) + free-form body (notes, links, status updates).
3. **Bidirectional sync.** `tools/task_sync.py` reconciles MTL ↔ backing files. Precedence rules: MTL line is the canonical surface for `text/area/priority/due/completion`; backing file is canonical for `notes/links/status_log`. Conflicts surface in a daily audit, never silently win.
4. **3-phase migration tool** (`scripts/migrate_threaded_tasks.py`): Plan → Apply → Verify. Plan emits a review report; Apply is idempotent; Verify round-trips on a vault snapshot.
5. **Audit script** (`scripts/audit_threaded_tasks.py`) runs every 15 minutes during cutover week, then daily. Surfaces: orphan backing files, orphan IDs, drift between MTL and backing, completion-sync mismatches.
6. **Command Center renderer** updates to thread cards (Dataview TASK queries with backing-file links).
7. **New runner endpoints:** `POST /tasks/split`, `POST /tasks/merge`, `POST /tasks/archive` on `services/oho_runner` — bearer-auth, asyncio-locked, verified-write.

## Hard rules

- IDs are immutable. Splits get new IDs that link back via `parent_id` in YAML. Merges fold under one ID with the others recorded in `merged_from`.
- Manual edits on phone (Remotely-Save round-trip) MUST survive a cron pass without ID loss. Audit catches drift within 15 min.
- Backing-file YAML schema is locked at v1; field additions OK, removals require schema version bump.
- Dataview queries in Command Center must continue to work during migration. Cutover is gated on round-trip test passing.

## Open questions (defer to Phase C kickoff)

- **OHO-side or LXC-side ID generation?** Spec recommends LXC-side via `tools/task_id.py` invoked through the runner sidecar.
- **YAML schema field set v1.** Spec §4 enumerates; review before locking.
- **Migration window.** Spec recommends 7-day "shadow mode" where backing files are written but Dataview still queries MTL only; then cutover.

## Consequences

- Unlocks: per-task analytics, decision journal binding ([Phase D](0007-master-plan-v2.md)), capture-everywhere idempotency (P3 envelope's `idempotency_key` chains to `task_id`), AI coach loops that need per-task history (P7).
- Adds a `30_Tasks/<area>/` subtree to the vault (8 areas × ~50 tasks = ~400 backing files at steady state).
- Increases MinIO write volume modestly (each task edit → backing file write); covered by the existing verified-write contract.

## Soak gate

ADR-0009 cannot land code until [ADR-0007](0007-master-plan-v2.md) Phase A soak closes (≥7 days clean, ending 2026-05-18 earliest). Per Master Plan v2 timeline, Phase C kickoff begins W3 (2026-05-19+).

## Rollback

Cutover is gated on the migration tool's Verify phase passing on a snapshot. If Verify fails: don't apply. If Apply happens but reveals drift in production: `scripts/migrate_threaded_tasks.py --revert` strips `[id::]` tags from MTL and quarantines backing files under `30_Tasks/.revert/` for post-mortem. No data loss path.
